# Refactoring Audit

Comprehensive refactoring audit of the MenuBarDeclutter codebase, generated by parallel
exploration subagents across App/Core, Settings/Onboarding, Hiding/Moving/StatusBar,
Accessibility/Search/SecondBar, Health/Profiles/Hotkeys/Permissions, and Tests/Project
structure.

Each finding references `file_path:line_number` for navigation. This document ranks
opportunities by impact and tracks the top-leverage actions separately so progress can be
followed.

## Summary

- **HIGH-impact findings:** 20
- **MEDIUM-impact findings:** 28
- **LOW-impact findings (quick wins):** ~20
- **Original test coverage gaps:** 7 pure-logic files without unit tests; follow-up waves
  now cover the pure logic and service behavior, with only the user-driven Accessibility
  permission prompt path left as system/manual coverage.
- **Top-leverage actions:** 5 (see "Highest-Leverage Actions" below)

## Risk Categories

- **P** = Performance gain
- **M** = Maintainability gain
- **C** = Correctness/race-condition fix

## HIGH-impact findings

### H1 — `SettingsStore` is a god-object without `@MainActor` and ~30 `didSet` clones
**File:** `MenuBar-Manager/Core/SettingsStore.swift:4-739`
**Categories:** C, M
**Issue:**
- Declared `@Observable final class` with **no `@MainActor`**, yet mutated only by
  `@MainActor` types (`AppEnvironment`, `SettingsRuntimeCoordinator`,
  `MenuBarItemSurfaceCoordinator`) and observed by SwiftUI Settings views. The compiler
  cannot prevent off-main mutation, and `@Observable` change notifications triggered off
  the main actor break SwiftUI's observation contract.
- ~30 stored properties each repeat the identical `didSet { defaults.set(x, forKey: ...) }`
  pattern. Optional ones repeat the `set`/`removeObject` variant. Clamped ones require a
  parallel backing field + computed property.
- Adding one setting requires touching **7 places**: `Key` enum, `register(defaults:)`,
  the 160-line `init` load block, `restoreDefaults()`, `DiagnosticsExporter.SettingsSnapshot`,
  `plainText`, and `json`.
- `init` performs write-back side effects (`defaults.set` to persist clamped values) at
  lines 461, 482, 499, 506, 519, 528.

**Suggested approach:**
1. Annotate `SettingsStore` with `@MainActor`.
2. Introduce a `@UserDefault`-style property wrapper that encapsulates `set`/`removeObject`/
   clamp behavior — collapsing the 30 `didSet` blocks and the 160-line `init` into
   declarative one-liners.
3. Consolidate the defaults table to a single source of truth
   (`static let defaults: [Key: Any]`) shared by `register(defaults:)`, `init`, and
   `restoreDefaults()`.

**Expected benefit:** ~400 lines removed; 7-place edit becomes 1-place; main-actor
correctness enforced for `@Observable` mutations.

### H2 — `DiagnosticsLogger` lacks `@MainActor` and `inferred(from:)` allocates on every log
**File:** `MenuBar-Manager/Core/DiagnosticsLogger.swift:59-88, 105-147, 138-142`
**Categories:** C, P
**Issue:**
- `@Observable` with mutable `events: [DiagnosticEvent]` but not `@MainActor`. Most callers
  are `@MainActor`, but nothing enforces it; `nonisolated` `DragExecutor` is a latent race
  risk.
- `DiagnosticCategory.inferred(from:)` runs on nearly every `log()` (default category
  param). It allocates `message.lowercased()` (full copy) then runs ~22 sequential
  `.contains` scans.
- `events.removeFirst(events.count - capacity)` is O(n) per overflow after saturation
  (capacity 200, burst logging).

**Suggested approach:**
1. Annotate `DiagnosticsLogger` with `@MainActor`.
2. Move inference off the hot path — have callers pass explicit `category:`; for the
   fallback, use case-insensitive `localizedStandardContains` without lowercasing, or
   compute lazily in the export path.
3. Replace `events` with a ring buffer for O(1) append/eviction.

### H3 — `DiagnosticsExporter` triplicates the settings schema and hand-rolls JSON
**File:** `MenuBar-Manager/Core/DiagnosticsExporter.swift:104-146, 167-211, 234-311, 341-437`
**Categories:** M, C
**Issue:** Settings schema stated 4× (`SettingsSnapshot` struct, `plainText`, `json`, plus
`SettingsStore` itself); `makeSettingsSnapshot` is a 43-line field-by-field copy; `json`
builds `[String: Any]` by hand with `NSNull()` for optionals — fragile, no compile-time
field coverage; `ISO8601DateFormatter` allocated per call.

**Suggested approach:**
1. Define a `Codable` `DiagnosticsSnapshotDTO` (and `SettingsSnapshotDTO`) and derive both
   JSON (via `JSONEncoder`) and plain-text key-value rendering from one declaration.
2. Reuse a cached formatter (`Date.ISO8601FormatStyle`) instead of allocating per call.

**Expected benefit:** 4-place edit → 1-place edit; ~120 lines of duplicated literals
removed; compile-time field coverage.

### H4 — `AppEnvironment` is a 725-line wiring god-object
**File:** `MenuBar-Manager/App/AppEnvironment.swift:1-725`
**Categories:** M
**Issue:**
- ~20 `lazy var` services hand-wired with `[weak self]` closure injections.
- `settingsWindowController` takes 17 closures; `menuBuilder` ~18 action closures;
  `statusBarController`, `menuBarItemSurfaceCoordinator`, `healthCoordinator`,
  `settingsRuntimeCoordinator` each 6-13.
- Duplicated `separatorFramesProvider` (×2, identical body).
- Duplicated `isHoverRevealSuppressed` closure (×3, identical body).
- `refreshSecondBarSettings`/`refreshSearchSettings`/`refreshBehaviorSettings`/
  `refreshTriggerSettings` redeclared as pass-through forwarding methods.
- Dead code: `applyProfile(named:)` (`:672-674`) — only caller is
  `ProfileAutomationCoordinator.swift:25` which calls a different method.
- `start()` performs 15 responsibilities; calls `runHealthCheck` twice (`:451`, `:455`).

**Suggested approach:**
1. Extract duplicated closures into single stored closure properties.
2. Group the 17 `settingsWindowController` callbacks into a `SettingsWindowActions`
   struct (or delegate protocol); do the same for `menuBuilder`.
3. Delete the dead `applyProfile(named:)`.
4. Split `start()` into sequenced `step*()` methods.

**Expected benefit:** ~50 lines of duplication/dead code removed; `start()` becomes auditable.

### H5 — `LiveStatusSection` reads ~40 `@Observable` properties in one SwiftUI body
**File:** `MenuBar-Manager/Settings/DiagnosticsSettingsView.swift:461-702`
**Categories:** P
**Issue:** `LiveStatusSection.body` reads ~40 fields of `LiveDiagnosticsStatus` in a single
35-row `Grid` plus `MenuBarSnapshotTable`. With Observation, a view registers dependencies
on every property it reads in `body`. Any single prop flip (`hoverPollingActive`,
`iconMoveInProgress`, `secondBarItemCount` all flip during normal operation) recomputes the
entire grid + snapshot table.

**Suggested approach:** Split into small sub-views, each reading only its own 1-3 fields
(`VisibilityStateRow`, `SeparatorMetricsRow`, `HotkeyStatusRow`, `SearchStatusRow`,
`SecondBarStatusRow`, `IconMoveStatusRow`, `ProfileStatusRow`).

**Expected benefit:** Recomputation shrinks from ~35 rows + table to one row per change.

### H6 — `HidingService.applyVisibility` dispatches observers even on no-op transitions
**File:** `MenuBar-Manager/Hiding/HidingService.swift:101-116`
**Categories:** P, M
**Issue:** No early return on `previousState == newState && !isReapply`. Single user click
landing on the same state triggers full observer dispatch; each observer writes 5
`@Observable` `liveStatus` fields + re-applies separators + calls `menuBuilder.refresh`
(no-op). Dual-channel observation (closures + NotificationCenter) fans out to 4 observer
paths.

**Suggested approach:**
1. Add `guard previousState != newState || isReapply else { return }`.
2. Pick one observation channel — closures *or* NotificationCenter, not both.

### H7 — `HoverRevealController.tick` recomputes screen geometry every poll even when expanded
**Files:** `MenuBar-Manager/Hiding/HoverRevealController.swift:122-140`;
         `MenuBar-Manager/Hiding/ScreenGeometryService.swift:54-72, 68-72`
**Categories:** P
**Issue:** `tick` calls `screenGeometry.isPointInAnyMenuBarBand(point)` on every 0.25s tick;
the band computation iterates `NSScreen.screens` and rebuilds `CGRect`s for each screen.
4×/second continuously while hover-reveal is enabled, even when expanded (so reveal cannot
fire). Bands only change on `didChangeScreenParametersNotification` but are recomputed
every tick.

**Suggested approach:**
1. In `tick`, read `isCollapsedProvider()` first; skip geometry call when not collapsed
   (unless `wasHovering`).
2. Cache bands in `ScreenGeometryService`; invalidate on display change (expose
   `invalidateCache()`).

### H8 — `IconMoveService.move` re-entrancy + `DragExecutor` no cancellation
**Files:** `MenuBar-Manager/Moving/IconMoveService.swift:97-238` (esp. `:121-149`);
         `MenuBar-Manager/Moving/DragExecutor.swift:15-45`;
         `MenuBar-Manager/App/MenuBarItemSurfaceCoordinator.swift:210-219`
**Categories:** C
**Issue:**
- `defaultConfirmation` calls `alert.runModal()` synchronously inside an `async @MainActor`
  function — spins a nested event loop that re-enters the main actor while `isMoving` is
  still `false` (`:139`). A second `move(...)` can pass the guard at `:101`.
- `DragExecutor.execute` never checks `Task.checkCancellation()` — once started, posts all
  events to completion even if cancelled.
- Caller (`MenuBarItemSurfaceCoordinator`) fire-and-forgets the `await` Task — no
  cancellation handle.

**Suggested approach:**
1. Set `isMoving = true` *before* presenting confirmation (or move confirmation out of the
   `async` path).
2. Add `try? await Task.checkCancellation()` inside `DragExecutor.execute`'s step loop and
   between down/up; propagate `CancellationError` as `.cancelled`.
3. Have caller store the move `Task` for cancellation on teardown.

### H10 — `AXMenuBarScanner` descends into dropdown menu subtrees
**File:** `MenuBar-Manager/Accessibility/AXMenuBarScanner.swift:99-166` (maxDepth 7, maxElements 700)
**Categories:** P
**Issue:** Recursive DFS into every child including `AXMenu` dropdowns under each
`AXMenuBarItem`. Every dropdown element fails `shouldIncludeSnapshot` (`:168-189`) — so the
scan pays full AX-read cost for hundreds of elements guaranteed to be excluded. Deep apps
(Adobe, JetBrains, browsers) crowd out actual status items from other apps via the shared
700-element cap.

**Suggested approach:** Prune traversal at the `AXMenuBarItem` level — once a snapshot is
recorded, do not recurse into its `AXMenu` child. Only descend into roles `AXMenuBar`,
`AXMenuBarItem`/`AXMenuExtra`/`AXStatusItem`. Typical reduction: hundreds → ~20-30 elements.

### H11 — `AXMenuBarScanner` does full per-app AX reads on every scan
**File:** `MenuBar-Manager/Accessibility/AXMenuBarScanner.swift:67-97`
**Categories:** P
**Issue:** Every scan calls `AXUIElementCreateApplication` + reads `kAXMenuBarAttribute` +
`readChildren` for every running application (30-60 apps → 60-180 AX round-trips). AX reads
are hundreds of µs cold, easily 50-150ms total. Scan runs on `@MainActor` — stalls UI.

**Suggested approach:**
1. Cache the set of pids that exposed `AXMenuBar` last scan; try cached set first; sweep
   full only on a longer interval or on `NSWorkspace` launch/terminate notifications.
2. Run scan off-main (`Task.detached(priority: .utility)`) and hop back to `MainActor` only
   when applying results to `liveStatus`. `AXUIElementCopyAttributeValue` is thread-safe.

**Expected benefit:** 2-5× scan-time reduction; UI responsiveness during scans.

### H12 — `SecondBarRootView.items` recomputed 5-7× per body
**File:** `MenuBar-Manager/SecondBar/SecondBarRootView.swift:20-39`
**Categories:** P
**Issue:** `items` calls `viewModel.items(from:query:)` (full filter × 2 + sort).
`hiddenItems`, `alwaysHiddenItems`, `itemIDs` each re-invoke `items` then `.filter`/`.map`.
Header reads `items.count`; `onChange(of: itemIDs)` rebuilds both `results` and `resultIDs`;
`selectFirstItemIfNeeded` recomputes again. SwiftUI does not memoize computed properties
across reads within one body.

**Suggested approach:** Compute `items` once into `@State` refreshed via `.onChange(of:)`
on actual inputs; or move derivation into `@Observable` `SecondBarViewModel` so view-model
owns the cache.

### H13 — `SearchService` allocates per-keystroke with no `SearchIndex`
**Files:** `MenuBar-Manager/Search/SearchService.swift:112-178`;
         `MenuBar-Manager/Search/SearchRootView.dart:21-31`
**Categories:** P
**Issue:** For each snapshot × keystroke, `bestMatch` calls `normalize(name)`,
`normalize(title)`, `normalize(bundleIdentifier)` — each does `.trimmingCharacters` +
`.folding(options: [.caseInsensitive, .diacriticInsensitive], locale: .current)` +
`.lowercased()`. 3 allocations × N snapshots × K keystrokes. `SearchRootView.results` is
recomputed on every body access (toolbar empty check, `ForEach`, footer count,
`selectFirstResultIfNeeded`, `moveSelection`, `activateSelectedResult`, `onChange(of:
resultIDs)`); no keystroke debounce.

**Suggested approach:**
1. Introduce `SearchIndex` (built once per scan, invalidated when
   `scannedMenuBarItems` changes) with pre-normalized strings.
2. Have `SearchService` own the index: `func update(snapshots:)` + `func results(query:)`.
3. Cache `results` in `@State`; debounce ~80-120ms.

### H14 — `SecondBarWindowController` has no display-change retraction
**File:** `MenuBar-Manager/SecondBar/SecondBarWindowController.swift:1-163`
**Categories:** C
**Issue:** Never registers `NSApplication.didChangeScreenParametersNotification`. On display
connect/disconnect/reorder, panel stays at old coordinates — potentially off-screen or
overlapping the dock. `positionPanel()` invoked only from `show()` and
`refreshAfterSettingsChanged()`.

`positionPanel()`; if `lastPosition` no longer inside any `NSScreen.visibleFrame`, reset
and close panel.

### H16 — `TriggerService` has no debounce/coalescing and applies in arbitrary order
**File:** `MenuBar-Manager/Profiles/TriggerService.swift:95-134, 179-219`
**Categories:** P, C
**Issue:**
- 3 event observers + 60s timer. Every callback immediately calls
  `evaluateCurrentContext(reason:)` which builds a fresh
  `TriggerEvaluationContext` enumerating `NSWorkspace.runningApplications`, querying
  `NSScreen.screens.count`, calling `IOPSCopy...`. `didActivateApplication` fires rapidly
  during alt-tabbing — N synchronous evaluations back-to-back.
- `evaluate()` iterates `triggers where shouldFire` and calls `fire()` for each with no
  priority/ordering; overlapping triggers apply in array order — "last array entry wins"
  with no documented precedence.
- `liveStatus.activeProfileID` written *after* `setVisibility` (`:117-119` of
  `ProfileApplicationService`) — second overlapping apply within the same eval loop may
  see stale `activeProfileID`.
- `fire()` calls `save()` per fired trigger — full atomic write once per match.

**Suggested approach:**
1. Single coalescing `Task` with ~250-500ms debounce window; cancel pending and reschedule
   per event.
2. Decide explicit precedence (e.g. first match wins; break after first fire).
3. Fold all `lastFiredAt` mutations into a single `save()` after the evaluation loop.
4. Make `applyBasicSettings` + `liveStatus.activeProfileID` atomic and ordered.

### H17 — `AutomationURLHandler` has no rate limiting, no caller verification, double decoding
**Files:** `MenuBar-Manager/Profiles/AutomationURLHandler.swift:29-99`;
         `MenuBar-Manager/Profiles/ProfileAutomationCoordinator.swift:102-109`
**Categories:** C, M, P
**Issue:**
- No authentication/throttle/sender identity check. Tight `menubardeclutter://profile/...`
  loop calls `profileStore.load()` (full directory scan + decode of every profile JSON)
  and `applyProfile` on every event — no back-pressure.
- Double percent-decoding: `path.first?.removingPercentEncoding` on already-decoded
  `url.pathComponents`. A profile name containing `%2520` is decoded twice — silent
  mismatch.
- Silent `false` returns on error; aliases `reveal-all`/`revealAll` undocumented.

**Suggested approach:**
1. Per-command throttle; log sender PID when available.
2. Use `url.pathComponents.first(where:)` directly; reject names still containing `%` after
   first decode.
3. Drop legacy aliases or move behind a feature flag.
4. Guard `install()` to refuse when automation disabled in Pro Mode.

## Implementation order

The five actions are sequenced in the order below so each can run `xcodebuild test`
independently and roll back safely:

1. **Action 5 (test scaffolding)** — reduces churn for later actions.
2. **Action 1 (Core refactor)** — foundational; touches most callers.
3. **Action 2 (AX scanner)** — independent of Core refactor.
4. **Action 3 (Search index)** — depends on AX scan output shape (unchanged by Action 2
   in the public surface).
5. **Action 4 (Trigger service)** — last; depends on health/profile wiring still intact.

After each action:
- `xcodebuild -scheme MenuBarDeclutter -destination 'platform=macOS' build`
- `xcodebuild test -scheme MenuBarDeclutter -destination 'platform=macOS'`

Failure to build stops work; the failing change is reverted before continuation.

### Notes on decisions deferred

- **Full `@UserDefault` property wrapper for `SettingsStore`** was deliberately not
  implemented. The audit identified it as the maintainability goal for H1, but the
  7-place entry-to-add-a-setting cost is currently manageable and the property-wrapper
  rewrite risks subtle behavioral drift around clamping-on-load, optional `set` vs
  `removeObject`, and registration semantics. The smaller wins (`@MainActor`, clamp
  consolidation) preserve all current behavior.
- **Codable consolidation of `DiagnosticsExporter`** was deferred. The JSON shape is
  loosely tested (`application`/`system`/`screens`/`settings`/`logs`/
  `excludedByDesign` keys exist, types match); a `Codable` migration is feasible but
  would still require a hand-rolled key-by-key `CodingKeys` declaration that mirrors
  the existing schema. The cached `ISO8601DateFormatter` removes the biggest per-call
  allocation, which is the higher-leverage win.
- **AXMenuBarScanner off-main scan** (remaining H11 work) was deferred because traversal
  pruning, candidate-pid caching, and workspace-driven cache invalidation now deliver the
  dominant AX-cost reductions while the off-main move requires verifying
  `DiagnosticsLogger` `Sendable` discipline and a hop-back-to-main bridge for
  `liveStatus` writes.
- **`.xcconfig` factoring** (M-TP1) was not added in this pass. Setting
  `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` on the test target handles the
  biggest test-target churn; xcconfig consolidation is a separate, lower-priority
  cleanup that does not affect runtime behavior.
- The unit-test target's `@MainActor` annotations on individual suites were not
  removed in bulk in this pass — they are now redundant (the target-level isolation
  setting makes them implicit) but harmless, and a mass edit would create churn
  unrelated to behavior. Future test edits can drop them opportunistically.
